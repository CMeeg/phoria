# Phase 4 — Canary & Release Workflow Design

## Purpose

Phase 4 gives Phoria a prerelease `beta` stream so integration and production testing runs against real published packages instead of local links, and it absorbs the `develop`-ahead-of-`main` integration through a `canary` branch rather than a single big-bang merge. It delivers the outcomes already scoped in `docs/PROJECT.md` Phase 4: a canary branch producing changesets-prerelease `beta` builds published to npm and NuGet; resolution of the unpublished-`@phoria/opentelemetry` docker blocker by syncing examples to published beta refs; examples that install and build against published packages as a release gate rather than per-PR CI; and — driven by npm's 2026-07-08 GAT 2FA-bypass deprecation — the move from a long-lived `NPM_TOKEN` to npm trusted publishing (OIDC). The problem definition, success criteria, and scope live in `docs/PROJECT.md` (Phase 4) and `docs/MEMORY.md` (2026-08-13 entries); this document decides *how*.

Non-goals: staged publishing (investigated and deferred — trusted publishing already satisfies the deprecation; see below), the `1.0.0` major releases and peer-range tightening (Phase 10), new example content (Phase 9), automating branch protection via `gh` (unavailable in this environment), and any per-package changesets config beyond the `baseBranch` switch.

## Current state (verified)

- Packages at `@phoria/phoria` 0.4.2, `phoria-react` 0.4.2, `phoria-svelte` 0.3.2, `phoria-vue` 0.3.2, `@phoria/opentelemetry` 0.1.0 (never published), `vite-plugin-dotnet-dev-certs` 0.2.1, and `phoria-dotnet` 0.4.2 (private, published to NuGet via `scripts/dotnet/publish.js`).
- 15 pending changesets, all minor or patch (Phases 1–3 work). The `1.0.0` major bumps stay queued for Phase 10.
- `release.yml` publishes from `main` on push using `NPM_TOKEN` + `NUGET_API_KEY`; `ci.yml` runs on `main` + `develop`; `develop` is 3 large commits ahead of `main`.
- Docker blocker root cause confirmed: `examples/getting-started/WebApp/package.json` references `@phoria/opentelemetry@^0.1.0`, which has never been published, and the committed lockfile omits it — so `pnpm install --frozen-lockfile` fails inside the Docker build.
- npm trusted-publishing prerequisites confirmed: every JS package's `repository.url` is `git+https://github.com/CMeeg/phoria.git`, and the Node 24 CI runners bundle npm ≥ 11.5.1.

## Branch model

- Create `canary` at the current `develop` HEAD and delete `develop`; feature PRs target `canary`.
- `ci.yml` triggers move from `develop` to `canary` (both `push` and `pull_request`).
- `main` receives only coordinated stable cuts from `canary`; nobody pushes to `main` or `canary` directly (branch protection).

## Prerelease setup (committed on `canary`)

- `.changeset/pre.json` is generated by `pnpm changeset pre enter beta` (`mode: "pre"`, `tag: "beta"`); changesets computes `initialVersions` from the current package state, so no hand-written version list.
- `.changeset/config.json` on `canary` sets `baseBranch: "canary"`; `main` keeps `baseBranch: "main"`. Each branch resolves its own committed config, which is how the stable and beta streams coexist in one workflow.
- The first beta run applies the 15 pending minor/patch changesets without a peer-range major cascade. The four `@phoria/phoria` peerers use `>=0.5.0-0 <2.0.0`, which satisfies the core's `0.5.0-beta.0` prerelease tuple, so frameworks remain on their natural 0.x prerelease versions and the peer ranges are not rewritten. Before a later beta cycle that changes the core tuple, update the lower bound to that upcoming tuple (for example, `>=0.6.0-0 <2.0.0`) in the same release preparation.
- Dist-tags: changesets applies the `beta` tag in pre mode and `latest` on stable. npm quirk: a never-published package's first publish also takes the `latest` tag — applies to `@phoria/opentelemetry`, accepted and documented.

## Single shared release workflow

The npm trusted-publisher constraint (below) forces one publish workflow file, so the earlier "separate `release-canary.yml`" idea is replaced by a single `release.yml` whose behavior is driven by repo state (pre.json present on `canary`, absent/exit on `main`), not by which branch pushed. Changes:

- trigger becomes `push: branches: [main, canary]`
- `permissions` gains `id-token: write`; the `NPM_TOKEN` env var is removed; `NUGET_API_KEY` is unchanged (nuget.org has no OIDC equivalent)
- the same `changesets/action` flow stays (`version: pnpm run version`, `publish: pnpm run publish`), and the existing `examples:bump` + `git push --follow-tags` steps now run on both branches so examples track beta refs on canary and stable refs on main

## npm trusted publishing (OIDC)

- Configured once per package on npmjs.com (Settings → Trusted Publisher): org `CMeeg`, repo `phoria`, workflow file `release.yml`, allowed action `npm publish`. npm allows exactly one trusted-publisher config per package — the source of the single-workflow constraint.
- During `changeset publish`, the npm CLI auto-detects GitHub OIDC from the workflow's `id-token` permission; provenance is added automatically for public packages. Do not set `NODE_AUTH_TOKEN` or any npm token env var.
- NuGet publishing is unchanged (`NUGET_API_KEY`, `scripts/dotnet/publish.js`), because nuget.org offers no OIDC trusted publishing.

## Staged publishing (deferred)

Investigated per `TODO.md`'s "npm publishing changes" item: `npm stage publish` replaces the live publish with a tarball a human approves with 2FA on npmjs.com. Deferred for three reasons. First, `changeset publish` has no staged mode, so staging the stable stream means replacing it with a custom per-package `npm stage publish` loop that re-implements dist-tag and git-tag handling. Second, a brand-new package cannot be staged, so `@phoria/opentelemetry`'s first publish must be direct regardless. Third, for a sole maintainer the human gates staging would add already exist as the changesets version PR, the canary→main cut, and branch protection — while trusted publishing alone fully satisfies the GAT deprecation. Revisit post-1.0 if the extra npm-level approval gate is wanted.

## Stable-cut runbook (documented in CONTRIBUTING.md)

1. On `canary`: run `pnpm changeset pre exit` and commit (`baseBranch` stays `canary`).
2. Merge `canary` into `main`. `main`'s `release.yml` cuts stable: version PR → merge → stable publish + `examples:bump`.
3. Merge `main` back into `canary`, then run `pnpm changeset pre enter beta` and commit.
4. Steps 1–3 form a quiescent window: `canary`'s `release.yml` publishes nothing because no changesets are pending and pre.json is in exit mode.

## Branch protection (applied via the GitHub web UI; `gh` is unavailable here)

Applied to both `main` and `canary`: require a pull request before merging (no direct pushes), require the CI status checks (`build-and-test`, `test-browser`), block force pushes, restrict who can push to maintainers, and allow admin bypass ("Do not allow bypassing the above settings" left unchecked — an emergency escape hatch on a solo repo). Required approvals are deliberately not enforced: GitHub never counts the PR author's own approval, so requiring approvals would deadlock a sole maintainer; enable them when a second active maintainer exists.

## CONTRIBUTING.md (new, repo root)

A public-facing contribution and release guide: prerequisites and local dev setup (`pnpm install`, `pnpm build`, `pnpm examples:link`, test commands), the branch model and contribution flow (fork → branch → `pnpm changeset` → PR to `canary` → CI checks → merge), the release workflow including the stable-cut runbook and examples sync, and how publishing is gated (branch protection, OIDC trusted publishing, NuGet API key).

## Rollout sequence (rehearsal → live)

0. Rehearsal on a throwaway worktree: update the peer tuple, run `pnpm changeset pre enter beta` → `pnpm run version` → inspect the resulting versions, unchanged peer ranges, and dotnet version sync → `pnpm changeset pre exit` → discard.
1. Apply branch protection (web UI) to `canary` + `main`.
2. Create `canary` at `develop` HEAD; delete `develop`; update `ci.yml` triggers.
3. On `canary`: set `baseBranch: "canary"` and run `pnpm changeset pre enter beta`; `main` stays unchanged.
4. Rewrite `release.yml`: branch trigger, `id-token: write`, drop `NPM_TOKEN`, examples sync on both branches.
5. Configure the six npm trusted publishers.
6. First canary run: version-PR merge → beta publish → `examples:bump` → verify the npm `beta` dist-tags, the NuGet beta, and `examples/getting-started` docker-compose `pnpm install --frozen-lockfile` against the published betas.

## Verification / success criteria

- A `canary` push opens a "Version Packages (beta)" PR; merging it publishes the recorded natural 0.x `0.5.0-beta.N`/`0.4.0-beta.N`/`0.2.0-beta.N` package versions with the `beta` dist-tag on npm and a matching beta on NuGet, with no `NPM_TOKEN` in the workflows and no `1.0.0-beta.N` peer cascade.
- `examples/getting-started` docker-compose builds against the published betas (the PROJECT.md docker success criterion).
- The stable-cut runbook produces a `0.5.0` stable release with `examples:bump` to stable refs, and `canary` returns to beta mode.
- `pnpm examples:check` passes on `canary` (refs point at real published betas).
- `pnpm build` → `pnpm lint` → `pnpm check` → `pnpm test` and `dotnet test --solution Phoria.sln --configuration Release` stay green.
